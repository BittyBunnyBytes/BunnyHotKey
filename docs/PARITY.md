# Parity with AutoHotkey v2

![Parity chart](../assets/parity.svg)

## How it's measured
Every percentage comes from running real scripts, not from reading BHK's source or from estimates.

- **Conformance suites** (`tests/conformance/*.ahk`, run by `tools/conformance.py`): one feature per section,
  each a standalone script whose console output is compared with the result AutoHotkey documents (checked
  against the v2.0.31 and v1.1 source where the docs are unclear; expectations never come from BHK). An
  area's percentage is its suite's pass rate. Suites marked `desktop` run on the real X11 session: they
  open BHK test windows, activate them and only then send synthetic keyboard/mouse input; the tray suite
  finds the script's icon in the panel (`tools/x11_tray_probe.py`) and clicks it.
- **Built-in groups:** the share of the group's functions (AutoHotkey v2.0.31's own function table, listed in
  `tools/ahk_builtins.txt`) that a passing run test calls: a passing conformance section or a v2 regression
  script (`tests/scripts`, run by `tests/run.py`).

  - Functions left out on purpose because a test would disturb the machine: `Shutdown`, `FileRecycleEmpty`,
    `BlockInput`, `WinMinimizeAll`/`WinMinimizeAllUndo`, `DriveEject`/`DriveRetract`/`DriveLock`/
    `DriveUnlock`/`DriveSetLabel`, `Edit`.
- **Real-world scripts:** 337 scripts from seven v2 repositories are loaded and compiled
  (`docs/COMPATIBILITY.md`); they're not executed (that would run downloaded third-party code).
- **v1:** the v1 suites (`v1_language`, `v1_gui`, `v1_hotkeys`), the v1.1 command table
  (`tools/ahk_v1_commands.txt`) and the public v1 script corpus (`tools/v1_corpus.py`).
- **Updating the chart:** `python3 tools/parity_chart.py` runs every suite (the desktop ones take a few minutes
  and need the X11 session), redraws `assets/parity.svg` and rewrites the marked blocks in `README.md` and this
  file. `docs/parity.json` holds the area names, notes and the "missing" list.
  `tests/run.py` runs the non-desktop suites against `tests/conformance/baseline.json`; set
  `BHK_DESKTOP_TESTS=1` to include the desktop ones.

## What's missing or left to do
| Area | Status | What's left |
|---|---|---|
| COM / ActiveX | 🟡 80% | COM objects are real native COM (`bunnyhotkey/lib/comnative.py`): every emulated object and every script object (`ObjPtr`) is an IDispatch vtable in memory, with VARIANT/BSTR marshalling, so `ComCall` (any vtable index), `ComObjQuery` (QueryInterface and QueryService), `ComObjFromPtr`, `ComObjValue`, `ObjAddRef`/`ObjRelease` and IDispatch pointers from native code all work. `ComObjActive` and `RegisterActiveObject`/`GetActiveObject` use a running-object table shared by BHK processes, with member calls (and callbacks) over IPC (`rot.py`). `CoCreateInstance`, `CLSIDFromString`, `SysAllocString` and friends are in the DllCall table. Emulated servers (the Wine approach, `com.py`): `WinHttp.WinHttpRequest.5.1` and `MSXML2.XMLHTTP`/`ServerXMLHTTP` (sync, async, `ComObjConnect` events, headers, `ResponseBody`), `Scripting.Dictionary`, `WScript.Shell` (`Run`, `Exec`, `Popup`, `RegRead/Write`, `SendKeys`, `ExpandEnvironmentStrings`, `CreateShortcut`, `SpecialFolders`), `Scripting.FileSystemObject` (+ `File`, `Folder`, `TextStream`), `ADODB.Stream`, `SAPI.SpVoice` (speech-dispatcher/espeak), `Shell.Application`, WMI via `ComObjGet("winmgmts:")` with WQL, and the ActiveX web browser. Not possible without Windows: servers that only exist as Windows binaries (Office, UIAutomation, WebView2...). |
| Wayland input | ❌ dropped for now | Hotkeys and Send need X11. A portal-based backend (GlobalShortcuts / RemoteDesktop) is the path forward. |
| Gui | 🟢 100% | All 23 control types. Custom controls take the standard Win32 classes (Button, Edit, Static, ComboBox, ListBox, SysListView32, SysTreeView32, msctls_*, SysDateTimePick32, SysMonthCal32, SysTabControl32, SysLink) plus SysIPAddress32 (`IPM_*`), RichEdit and Scintilla (`SCI_*`), and raise only `OnCommand`/`OnNotify`, as on Windows. Also including MonthCal `Multi` ranges (Shift+click) and StatusBar parts with their widths. The ActiveX control hosts the web browser (`Shell.Explorer`, a URL or `mshtml:<html>`) through WebKitGTK when `webkit2gtk-4.1` is installed, with `Navigate`, `LocationURL`, `GoBack`, `Document.write` and `execScript`; this path couldn't be tested on the development machine, which lacks WebKitGTK. Other ActiveX controls and window classes a script registers itself host Win32 components and can't exist on Linux. Widgets use the GTK theme's metrics, so default control sizes differ slightly from Windows. |
| Win32 controls | 🟢 100% | Complete for the script's own Gui windows, including Win32 control messages through SendMessage/PostMessage (`ctlmsg.py`: `WM_GETTEXT`, `EM_*`, `LB_*`, `CB_*`, `BM_*`, `PBM_*`, `TBM_*`, `UDM_*`, `HKM_*`, `SB_*`, `TCM_*`, `LVM_*`, `TVM_*`) and notifications with Win32's codes (`notify.py`: `OnCommand` with `BN_CLICKED`/`EN_CHANGE`/`LBN_SELCHANGE`..., `OnNotify` with an NMHDR/NMLISTVIEW/NMTREEVIEW for `NM_CLICK`/`LVN_ITEMCHANGED`/`TVN_SELCHANGED`..., `OnMessage(WM_COMMAND/WM_NOTIFY/WM_HSCROLL)` on the Gui). Other programs' controls come from AT-SPI, the Linux accessibility bus (`bunnyhotkey/lib/atspi_.py`): widgets get Win32 class names by role (`Edit`, `Button`, `ComboBox`, `SysListView32`...), ClassNN numbering and stable HWNDs, and `ControlGetText/SetText`, `ControlClick`, `ControlGet/SetChecked`, `ControlChoose*`, `ControlGetItems/Choice/Index`, `ControlFocus`, `ControlGetPos`, `Edit*`, `ListViewGetContent`, `StatusBarGetText/Wait`, `WinGetText`, WinText matching, `WinGetControls` and `MenuSelect` work on them, and so do the common control messages (`WM_GETTEXT`/`SETTEXT`, `BM_*`, `CB_*`/`LB_*`, `EM_*` selection and lines, `TBM_*`/`PBM_*`/`UDM_*` through the AT-SPI Value interface, `TCM_*`, `LVM_*` counts and selection) (`tests/run_live.py` and `tests/live/run_foreign_messages.py` drive a separate GTK app). Left: AT-SPI can't move, show/hide or restyle another program's widget or add/delete its list items (those raise OSError), and apps that don't publish accessibility data stay opaque (Qt needs `QT_ACCESSIBILITY=1`, Chromium/Electron `--force-renderer-accessibility`). |
| DllCall | 🟡 partial | About 45 common Win32 APIs are emulated (including `EnumWindows`, `SendMessage`, `IsWindow`). Calls into any Linux `.so`, calls by address, `CallbackCreate` trampolines, native pointers and `#DllLoad` of `.so` libraries (callable by bare function name) work. Arbitrary Windows DLLs don't; `#DllLoad` of one is skipped so the script still loads. |
| Window messages | 🟢 | `OnMessage`, `SendMessage` and `PostMessage` work for the script's own windows and controls and between BHK scripts. Each script has AutoHotkey's hidden main window (`A_ScriptHwnd`, class `AutoHotkey`, title `path - AutoHotkey v2.0.31`), which answers `WM_COPYDATA`, `WM_CLOSE` and the tray/main-menu `WM_COMMAND` IDs (65300-65307, 65400-65409). Common Win32 messages (`WM_SYSCOMMAND`, `BM_CLICK`, `CB_SETCURSEL`, `WM_SETTEXT`...) are translated. Non-BHK X11 programs have no Win32 message queue to receive them. |
| Hotkeys (X11) | 🟢 100% | `SendLevel`/`#InputLevel`/`MinSendLevel` follow AutoHotkey's rules (RegisterHotkey-style hotkeys see any sent input; hook hotkeys, hotstrings and InputHooks only higher levels). A bare-modifier hotkey (`LWin::`) suppresses the modifier: while it's unconditional the key leaves X's modifier map, so Win+E types "e" (a watchdog restores the map if the script dies). Hotstrings swallow their end key and re-send it after the replacement. `#HotIf`-conditional bare-modifier hotkeys take the key out of the modifier map only while their condition holds, re-checked whenever the active window changes. A `*` hotstring swallows its final character. |
| Window functions | 🟢 96% | `WinSetRegion` and `WinSetTransColor` use the X Shape extension; a colour key is a snapshot of the window's current pixels, so content drawn later isn't keyed. `WinGetStyle`/`WinSetStyle` map caption, border, system menu, sizing frame and min/max boxes to the Motif hints every X11 window manager honours, and visible/minimized/maximized/disabled to the window state. `WinSetEnabled` works on the script's own windows; X11 can't disable another program's window (OSError). `WinSetExStyle` maps always-on-top. |
| Files / Drives | 🟡 86% | `DriveGetLabel`, `DriveGetSerial`, `DriveGetType` and `DriveGetFileSystem` read the real mounts. `DriveSetLabel` runs the filesystem's label tool, which usually needs root. The drive eject/lock/label functions and `FileRecycleEmpty` aren't run-tested (they'd act on the machine's hardware or Trash), which is why the row is below 90%. |
| Tray | 🟢 100% | Clicks follow MainWindowProc's AHK_NOTIFYICON handling: every press, release and double-click (left, right, middle) reaches `OnMessage(0x404)` first (wParam 1028, lParam `WM_LBUTTONDOWN`...), and a non-blank return cancels the default action; then the default item runs on a double-click (single click with `ClickCount 1`) and the menu opens on right-button-up. `TrayTip` balloons report `NIN_BALLOONSHOW/USERCLICK/TIMEOUT/HIDE` the same way, honour the Mute and tray-icon options, and `TrayTip()` hides the current one. `A_TrayMenu` supports submenus, radio items, icons and colours like any Menu. Verified live on XFCE; on Cinnamon through XApp's StatusIconMonitor, the mechanism Cinnamon's tray applet uses. AppIndicator-only panels (KDE/GNOME) open the menu themselves and don't report clicks. |
| Audio | 🟢 | `Sound*` functions take AutoHotkey's Device parameter (number, or name substring with `:N`) over PulseAudio/PipeWire (`pactl`): playback devices first, then recording devices. Only the endpoint ("Master") component exists; other component names raise TargetError. `SoundGetInterface` returns native IAudioEndpointVolume, IAudioMeterInformation (peak levels from `parec`), IMMEndpoint and, for the Master component, IAudioVolumeLevel/IAudioMute, with the Windows SDK vtable layouts for `ComCall`. |
| System variables | 🟢 | `A_Language` (from the locale), `A_ScreenDPI` (Xft.dpi), `A_Cursor` (XFixes), `A_IconFile`/`A_IconNumber`, `A_AllowMainWindow` and `CaretGetPos` (AT-SPI) reflect the real state. `A_OSVersion` deliberately reports Windows 10 so version checks in scripts pass. |
| Diagnostics | 🟢 | `ListLines` (last 400 executed lines with elapsed times, per-thread on/off), `ListVars`, `ListHotkeys` and `KeyHistory` open AutoHotkey-style windows. |
| AutoHotkey v2.1-alpha | ⚪ not targeted | Typed properties, structs and `#Module` are v2.1-alpha features. BHK targets v2.0. |
| AutoHotkey v1 | ⚪ out of scope | v1 scripts get a clear message. |
